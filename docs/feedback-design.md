# blockmancala：配置・連鎖・全消しの手応え

既存の青い盤面、宝石の4面とテーブル面、左上の光源、影の方向を保ったまま、操作の瞬間と成功の段階を聴き分け・見分けやすくする変更。

## 参考動画から読み取ったこと

提供された `812566476.615965.mp4` は約60.84秒、590×1280の画面収録。SNS上で再生されたプレイ映像なので、以下の時刻は収録内の目安。100msごとのフレーム比較を使い、アプリ内部の正確な遅延値とは区別した。参考映像や音源のデータはゲームに同梱していない。

| 場面 | 観察 | 今回の実装への反映 |
| --- | --- | --- |
| 2.7〜3.2秒付近 | 置く前に対象ラインが同じ色になる。確定・消去・残像・得点が短い間に順番に起こる | 既存の予告を活かし、配置の短い接触音、溜め、ラインの弾み、ゴールの音を別の出来事として組む |
| 17.4〜18.4秒付近 | 複数ラインの予告→消去→COMBO→得点の流れ。次の操作中にも余韻が残る | マンカラの配布を追える移動速度は保ち、連鎖ごとの音程と成功段階の和音に差を付ける |
| 45.8〜47秒付近 | 通常消去のあと、空の盤面が見える全消しの見せ場になる | 全消しに専用フレーズを用意。宝石の波は短い余韻にし、次の配置で表示を引く |

参考音声はモノラルPCMへ展開して波形・周波数を確認した。収録では約240Hz付近を含む持続成分が強く、単純な音量閾値で配置音と消去音を分離できない。個々の原音の音程・音量・立ち上がり時間を正確に測れたとはしていない。また、この環境では添付音声の直接試聴を行えていない。ここで採用した音色は、イベントの役割と元のゲームの設計を踏まえて新しく合成したもの。

## 実装した音

- **つかむ**：短い上向きの音。置く音より控えめ。
- **置く**：36msの接触音、95msの低い胴鳴り、100〜130msの余韻。4種類の微差を循環させ、1〜9マスで胴鳴りの高さ・振動を変える。
- **ぴったり**：独立した接触音と上昇する2音。配置の弾みも少し強くする。
- **発動**：溜めに短い上昇音を追加。解放は割れ音・低音・空気の抜ける音の3層。ラインの長さで厚み、連鎖で音程を変える。
- **流れる**：位置の進行に合わせた細かい音。追いつくための早送り時は抑える。
- **ゴール**：本音・5度・低い着地音。4連鎖から和音、8連鎖から後打ちを足す。同時到達は1回にまとめる。
- **成功段階**：Good / Great / Excellent / Amazing / Unbelievable の段階が上がったときだけ和音を鳴らす。同段階の連鎖はゴール音が主役。
- **全消し**：上昇フレーズと落ち着く和音。宝石が砕ける瞬間には別の短い音を同期する。

旋律は2オクターブのペンタトニック。長い連鎖はフレーズを循環する。高音を固定の上限へ切り揃えていた処理を、オクターブを下げる処理へ変更した。出音にはローパスとコンプレッサーを通す。同時発音40音を上限にし、操作音を装飾音より優先する。

## 見た目とテンポ

- 通常着地240ms、ぴったり着地290ms。ピース内のずれは最大36ms。
- 初回発動の溜め150ms、1マスの移動60ms、連鎖間70msは従来どおり。ルール・配布・得点計算は変更していない。
- 列からの移動中はブロックと盤面の拡縮・揺れを止める。溜めの縮みは宝石の面だけに掛け、座標を持つ親要素は拡縮しない。かけらのサイズは盤面のマス幅を基準にする。
- ゴールは小さく縮む→膨らむ→戻る。入った色のかけらを出し、元のブロックを濃さを変えずに縮める。
- 全消しの宝石1個の寿命は1150msから760ms、輪の間隔は75msから55msへ。かけらは通常最大14個、全消し最大42個。
- かけらは既存の `gemSprite` を再利用。光源を揃えるため回転させず、色を薄くせず縮めて消す。
- 一時停止・再開に遅延処理と盤面内のアニメーションを同期。次の配置では全消しの宝石を引き、予約された追加の破裂を無効にする。
- 低負荷設定・`prefers-reduced-motion` では揺れや飛び散りを抑える。

### 調べたこと（音）

ネットで調べた範囲（要約を読んだもの。サイトによってはこの環境から開けなかった）と、そこから使った考え方:

- **ガラスの音はモーダル合成で作れる**: 叩かれたガラスは、いくつかの固有の振動（モード）が、それぞれの速さで消えながら鳴る。
  「ノイズといくつかの値だけでガラスを叩く音を作る」例（GitHub の `suchipi/modal-synthesis` と `modal-synthesis-example`）と同じ考え方。
  ワイングラスの (2,0)・(3,0)・(4,0) モードの研究（UNSW の Jundt ら）では、整数でない周波数のモードが、それぞれ別の減衰時間で重なって聞こえる。
  市販のグラスの共鳴は 約 0.45〜1.8kHz、手でテーブルに触れて止めるような減衰は 0.15 秒で約 35dB（計測例の要約）。
- **バーチャイム（マークツリー）の音**: 直径約 3/8 インチ（約 9.5mm）のアルミ・真鍮の棒を、長さを変えて吊るした楽器。25〜36 本のものは棒の長さが
  3〜8 インチ（約 8〜20cm）。指やバチでなでると、高い音が駆け上がる（グリッサンド）。はっきりした音の高さはなく（整数倍でない部分音）、
  きらめく金属の音が数秒かけて消える（ショップ・辞典・Wikipedia の説明の要約）。
  - 棒の長さから基本の高さを求めた**自分の計算**: 両端が自由な棒の曲げ振動は f₁ = (4.73² / 2π) · r · c / L²（r = 直径 / 4 = 2.4mm、c = √(E/ρ) ≈ 5050m/s）≈ 42.8 / L²。
    L = 20cm で約 1.1kHz、7.6cm で約 7.4kHz。つまり基本の高さは 1〜7kHz
  - 部分音の比は、同じ式の係数 β·L = 4.730, 7.853, 10.996, 14.137 から 1 : 2.756 : 5.404 : 8.933（グロッケンのバーと同じ）
  - うなり（ほぼ同じ高さの 2 つの部分音の干渉）が金属のきらめきになる（ほぼ同じ高さに割れた対）
- 「シャンシャン」「尖った」の受け取り方（**自分の解釈**。新しく調べたものではない）: 「シャンシャン」は鈴・タンバリン・神楽鈴の擬音で、短い金属の「シャッ」と
  そのあとの響きが、続けて何度も鳴る音。「尖った」は、3kHz 以上に音の大きさが寄った（心理音響のシャープネスが高い）、立ち上がりの速い音。
  そこで、(1) バーチャイムを 2 回なでる、(2) 硬く叩いたときの高い部分音、(3) 叩く瞬間の「チッ」と、擦れ合う「シャッ」の雑音、
  (4) 聞こえる大きさと長さは直前の版と同じ（前に「音の長さはそのまま」と言われたので）、の 4 つにした
- 最初の版（クリスマスのベル + 鈴）は、教会の鐘の部分音（ハム・プライム・ティアス・クイント・ノミナル）と、Perry Cook の PhISEM（STK の Shakers）の
  「ランダムな衝突が共振を鳴らす」考え方で作ったが、イメージは写真のバーチャイムだった（低く、ベル寄り）ので、バーチャイムに作り直した。

### 実装した音

- **ガラスを置く音**（`glassBuffer`、約 0.5 秒）。コップの高さ 4 種（1.56・1.76・1.98・2.21kHz）を順番に使う。
  - 共鳴の周波数比 1 : 2.83 : 5.42 : 8.77 は、薄い円筒殻の曲げ振動の式 m(m²−1)/√(m²+1)（m = 2, 3, 4, 5）から**自分で求めた値**（出典から写したものではない。
    金属のバーの 1 : 2.756 : 5.404 : 8.933 とほぼ同じ種類の比になる）。そこに軸方向のモード（1.52 倍・4.1 倍）を足す。
    消えるまでの時間（60dB）は 0.30 / 0.19 / 0.11 / 0.06 秒と、高いほど速い。基本モードは 1.006 倍にずれた対にして、うなりを出す
  - 接触の「カチッ」（0.6ms で消える雑音）+ 底がテーブルに当たる 185〜210Hz の「コツ」（約 55ms）+ 21〜27ms 後の小さな再接触（30%）
  - 再生の速さを 1〜0.86 倍にして、大きいピースほど低く（大きいコップ）。毎回 ±2% ばらす
  - 旧版は 621 / 188 / 938Hz の低い「ボコッ」だった。新しい音は 1.65 / 4.7 / 8.9kHz のガラスの響きが乗る（OfflineAudioContext のスペクトルで確認）
- **シャラン**（`shalanBuffer`、1.3 秒。聞こえるのは約 1 秒）: バーチャイムを指で 2 回なでたときの、尖った「シャン、シャン」。
  - 最後のバー（「ン」）の高さは、ゴールの音（`note(chain - 1, 330)`）と同じ音階の 3 オクターブ上を 2〜4.5kHz に折りたたんだ
    2220 / 2492 / 2797 / 3326 / 3734 / 4440Hz（連鎖 1〜6。7 連鎖目から 2 連鎖目以降と同じ高さに戻る）。高さごとに波形を合成する（再生の速さで高さを変えると、
    長さも変わってしまう。最初の版は連鎖 1 で 1.3 倍の長さ、連鎖 6 で 0.6 倍の長さになっていた）
  - **1 回目のなで上げ**: 一番低いバー（約 1.1kHz）から最後のバーまで、半音ごとに 12〜24 本のバー（連鎖 1 は 12 本、連鎖 6 は 24 本）を、
    0.115 秒で順に叩く（間隔 9.6ms〜4.8ms）。大きさは 0.06 → 0.28 とだんだん強く（間の半音のバーは 0.34 倍）。ペンタトニックの音のバー
    （最後のバーの 3・5・8・10・12 半音下）は 0.2〜0.38 秒、間の半音のバーは 0.10〜0.18 秒で消える（60dB）。最後のバーは 0.123 秒に叩く
    （余韻 0.2 秒の短い「チン」+ 40ms の「シャッ」）。
    **2 回目**: 最後のバーの 7 半音下から最後のバーまで 7 本を 0.07 秒で（0.2 秒から。強さ 0.85 倍）、最後のバーを 0.278 秒に叩く
    （0.7 秒で 60dB 小さくなる長い響き + 40ms の「シャッ」）。2 つの「シャッ」の間隔は約 0.155 秒
  - **尖った音にした工夫**: 金属のバーの部分音 1 : 2.756 : 5.404 : 8.933 を、硬く叩いたときの強さにした（大きさ 1 : 0.6 : 0.4 : 0.2、消える速さ
    1 : 0.55 : 0.4 : 0.25。直前の版（バーチャイムの最初の版）は 1 : 0.35 : 0.12 : 0.04）+ 1.001〜1.0017 倍にずれた対（0.55 倍）+ 叩いた瞬間の「チッ」（0.3ms で消える雑音）+
    擦れ合う「シャッ」（中心 5.2kHz・Q 0.8 の帯域雑音。0.6ms で立ち上がり、バーごとに 12ms、最後のバーは 40ms。大きさはバーの 2.4〜2.6 倍）。
    「シャッ」は部分音とは別の層に足し、こだまは部分音の層だけに掛ける（雑音まで重ねると、2 回が 5 回に聞こえる）。
    モードごとの向き（符号）は、打った場所での振動の向きがモードごとに違うのでばらばらにする（そろえると、打った瞬間に全部が重なって
    鋭いピークになり、そのぶん全体の音量を上げられない）。バーごとに乱数を固定して、高さが違っても同じ位置のバーは同じ鳴り方
  - 短いこだま 2 つ（83ms・151ms。0.22・0.12 倍。部分音の層だけ）。先頭 1 秒の RMS を、出口の 9.5kHz のローパスを通したあとの大きさでそろえる
    （聞こえない 9.5kHz 以上の部分音・雑音は数えない）。最大の振幅は 0.98 まで（尖ったぶん山が高く、RMS 0.073〜0.077 で最大 0.66〜0.94）
  - 大きさ（出口の前の音量）: 波形の RMS を 0.147 → 0.07 に下げたぶん、通常のラインは 0.312（連鎖の 2 番目以降は 0.384）、全消し・新記録は
    0.48（全消しの 2 回目は 0.408）。ガラスの置く音は 0.58
- **鈴**（`bellBuffer`、1 秒）: 「薄っぺらい」と言われた、音の高さのある「ピン」の音（ゴール・手駒の補充・ぴったり・コンボ・褒め言葉・砕ける音・
  ファンファーレ・全消しの駆け上がり）。**何がそう聞こえていたか**: どれも `tone()` の正弦波・三角波で、パワーの 99% が 500Hz 以下・重心は 280〜420Hz（連鎖 1・コンボ 2・褒め言葉 1）、
  1kHz 以上はほぼ 0（実際の出口で測定）。スマホの小さなスピーカーは 500Hz 前後より下がほとんど出ないので、基本の音が消えて細い「ポッ」だけになる
  （ここは自分の推測。実機のスピーカーでは測っていない）。長さも 40〜200ms と短かった。
  - 波形: 部分音 [比 : 大きさ : 消える速さ] = 0.5 : 0.3 : 1.3（胴の低い響き）/ 1 : 1 : 1（基本）/ 2 : 0.8 : 0.7（オクターブ上）/ 2.756 : 0.55 : 0.45 /
    3 : 0.3 : 0.5 / 5.404 : 0.32 : 0.25 / 8.933 : 0.12 : 0.12（2.756・5.404・8.933 は金属の曲げ振動の比。シャランのバーと同じ）+ 基本の 1.0028〜1.004 倍にずれた対（0.55 倍。
    ゆっくりしたうなり）+ オクターブのずれた対 + 打った瞬間の「チッ」（0.4ms）+ こだま 2 つ（43ms・97ms。0.16・0.09 倍）。基本が 60dB 消えるまで 0.62 秒 ×（700Hz / f）^0.35。
    乱数は高さごとに固定。先頭 0.4 秒の RMS（9.5kHz のローパスを通したあと）を高さによらずそろえる
  - 高さ: 鈴は 11 個の波形（392 × 2^(k/4)。392〜2217Hz）を作っておき、いちばん近いものを再生の速さ ±9% 以内で合わせる（部分音の比は変わらない）。
    ゴールの音は 1 オクターブ上げる（連鎖 1 = 555Hz、10 連鎖 = 1865Hz。同じ音階で、10 連鎖まで折り返さない）。ぴったり・補充・砕ける音・ファンファーレは元の高さのまま、
    コンボ・褒め言葉・全消しの駆け上がりは 1 オクターブ上げる
  - 鳴らし方: 1 つの鈴 = 1 ボイス（明るい出口）。波形の自然な減衰に、さらに `ring` 秒で 60dB 消える減衰を重ねて響きの長さを決め、聞こえなくなるころにボイスを止める
    （ゴールの根音 1.1・5 度 0.8・3 度 0.45、補充・ぴったり 0.45、コンボ 0.6、褒め言葉 0.7 + 段階 × 0.08、砕ける 0.4、ファンファーレ 0.6（最後 1.4）、全消し 0.5（最後 1.4））。
    ゴールは根音 + 5 度（25ms 後）+（4 連鎖から）3 度（50ms 後）+ 低い着地音（正弦波のまま）。オクターブ上は鈴の部分音に入っているので足さない
  - 大きさ: 連鎖が進むほど強く（ゴール 0.385 → 0.67。前の音も進むほど大きかった）、褒め言葉は段階が進むほど強く。前の音と、耳の感度で重み付けした RMS（先頭 0.6 秒。
    全消し・ファンファーレは 1.2〜1.5 秒）がそろうように、音ごとに測って決めた（新 / 旧 = ゴール 1.04〜1.17 倍、補充 1.08、ぴったり 1.07、コンボ 0.99〜1.18、
    褒め言葉 1.02〜1.12、砕ける 1.09、ファンファーレ 1.02、全消し 1.05）
  - 測定（実際の出口。前の版 → 今の版）: パワーの重心 ゴール 1 連鎖 334 → 948Hz・3 連鎖 415 → 1249Hz・8 連鎖 862 → 2482Hz。500Hz 以下の割合 0.99 → 0.16（ゴール 1 連鎖）、
    0.98 → 0.38（コンボ 2）、0.99 → 0.28（褒め言葉 1）。−40dB まで 0.16〜0.24 秒 → 0.24〜0.38 秒。450Hz 以下を切った「小さなスピーカー」風の大きさは、
    ゴール 1 連鎖 1.9 倍・3 連鎖 1.6 倍・コンボ 2 / 褒め言葉 1 が 2.3 倍、高い連鎖（8・10）や補充・ぴったり・砕ける音は 1.0 倍（もともと高い音）
  - 同時発音: 長い連鎖の最悪ケース（ゴール 40 回を 60ms ごと + 刻み・発動・シャラン・コンボ・褒め言葉）で、同時発音は前の版 34 → 40（上限ちょうど。奪い合いは 0 回）。
    実際のゲーム（ヒントで 84 手）は最大 17 のまま
  - 合成にかかる時間: 鈴 1 つ 約 2ms（11 個で約 20ms。起動後の空き時間に 1 つずつ作る）
- 配置: 置く音 = ガラス（優先度 3）+ 低い胴鳴り、満杯のライン = シャラン（優先度 1）、全消し = シャラン 2 回（0.06 秒後・0.5 秒後）、新記録 = 1 回（0.08 秒後）
- 作り方: 消えていく正弦波は 2 極の共振の式で足していく（毎サンプルの sin を使わない）。立ち上がりの段差はガラスで 0.1ms、バーで 0.4ms
  かけてなめらかにする（段差が残ると低い「パチッ」というクリックになる）。

    （直前のバーチャイム版 0.0153〜0.0157 と同じ大きさ）。最大から 40dB 下がるまで 0.80 / 0.80 / 0.76 / 0.86 / 0.84 / 0.72 秒（直前の版 0.62〜0.86 秒。
    長さは同じ）。ピークは 0.11〜0.15（直前の版 0.07〜0.09。同じ大きさで、はじける瞬間のピークが 2〜6dB 高い）

### 音のセット（スコアでローテーション）

「何種類か作ってもらった音を、まとめて鳴らすのではなく、500 点・1000 点ごとなどでローテーションしてほしい」への対応。実装は `synth.js`（`KITS`・`placeBuffer` / `chimeBuffer` / `noteBuffer`）・
`sfx.js`（`kitForScore`・`KIT_EVERY`・`Sfx.setKit`）・`main.js`（ターンごとの切り替え）。

- **セット**: 0 = ガラス（今までのガラスのコップ + バーチャイム + 鈴。波形は完全に同じ）/ 1 = 木琴 / 2 = オルゴール。
  置く音（高さ違い 4 種）・シャラン（最後の音の高さ 6 種）・鈴（高さ 11 段）の 3 種類を、セットごとの楽器で作る。持ち上げ・なぞる・置けない・解放・刻みなどの短い操作の音は、どのセットも同じ
- **切り替え**: スコアが `KIT_EVERY = 1000` 点進むごとに次のセットへ（`kitForScore(score) = floor(score / 1000) % 3`。3000 点で最初へ戻る）。
  ユーザーが例に挙げた 500 点・1000 点のうち 1000 点にした（このゲームは 1 回の連鎖で数百点〜数千点が入るので、500 点だと 1〜2 手ごとに替わってしまう。
  `KIT_EVERY` を書き換えるだけで変えられる）。**ターンの始まりのスコア**（前のターンが終わったときのスコア）で決めるので、1 つの連鎖の途中で楽器が替わらない。
  置く音はターンの番号つきで鳴らし（`place(cells, kit)`）、前のターンの再生が残っていても、そのターンの楽器で鳴る。再生は順番待ちなので、そのターンの再生が始まるとき（`playTurn`）に
  セットを替える。新しいゲームはガラス、途中から再開したときはそのスコアのセット、チュートリアルは常にガラス
- **木琴（マリンバ）**: ローズウッドの棒を撥で叩く。棒は中央を削って調律されていて、部分音は基本の 1 : 約 4 : 約 10 倍（実際の木琴の棒の値を、整数に近い比で表した）。
  金属の棒の 1 : 2.756 : 5.404 : 8.933 とは違って整数に近いので、音の高さがはっきりして丸く温かい。大きさ 1 : 0.34 : 0.1（硬い撥ほど高い部分音が強い）、
  消える速さは基本に対して 1 : 0.3 : 0.1。基本が消えるまで（60dB）は低い棒ほど長い（`0.9 × (523/f)^0.55` 秒。0.25〜1.4 秒）。
  共鳴管の低い響き（0.5 倍・基本の 1/10 の大きさ）とわずかにずれた対（1.0016 倍）、撥が木に当たる「コッ」（中心 f×2.4・最大 3.2kHz の帯域雑音 7ms）を足す
  - 置く音（0.45 秒）: ミ・ソ・レ・ラ（659 / 784 / 587 / 880Hz）の 4 種。硬い撥で叩く「ポコッ」+ 底がテーブルに当たる 175〜200Hz の「コツ」（ガラスと同じ）+ 24〜30ms 後の小さな再接触
  - シャラン（1.3 秒）: 棒をなで上げる「コロロン、コロン」。最後の棒の高さはバーチャイムの 1 オクターブ下（1110〜2220Hz。連鎖が進むほど高い）。1 回目は 22 半音下から 10 本のペンタトニックの棒を
    0.15 秒で（だんだん強く）、2 回目は 10 半音下から 5 本を 0.085 秒で（0.22 秒から）。最後の棒は 2 回目のあと 0.75 秒で 60dB 消える長い響き。こだま 2 つ（61ms・137ms）
  - 鈴の代わり（1 秒）: 毛糸の撥でやわらかく叩く 1 音
- **オルゴール**: 鋼のくしの歯（片持ち梁）をピンが弾く。片持ち梁の曲げ振動の部分音は 1 : 6.267 : 17.55 : 34.4（β·L = 1.875, 4.694, 7.855, 10.996 から。両端が自由な
  棒の 1 : 2.756 : 5.404 : 8.933 より、上の部分音がずっと高く離れる）。細く澄んだ基本に、すぐ消える高い「チリン」（大きさ 0.42 倍・消える速さ 0.22 倍）が混ざる。
  ピンが歯を弾く「ぴっ」（0.4ms で消える雑音）と、木の箱の胴鳴り（205 / 430 / 790Hz の短い共鳴）を足す。基本が消えるまでは `1.0 × (700/f)^0.4` 秒（0.35〜1.5 秒）
  - 置く音（0.5 秒）: ド・レ・ラ・ミ（1046 / 1175 / 880 / 1319Hz）の 4 種。「ポロン」。上の部分音（6.27 倍）が出口のローパス（9.5kHz）より下に入る高さにした（最初は 1.3〜2.1kHz にしたら、
    上の部分音が 9.8kHz 以上に出て、ほぼ純粋な正弦波の細い音になったので、下げた）
  - シャラン（1.3 秒）: 歯をなで上げる「ティロリン、ティロリン」。最後の歯の高さはバーチャイムと同じ（2.2〜4.4kHz）。1 回目は 22 半音下から 10 本を 0.11 秒で、2 回目は 10 半音下から 5 本を 0.065 秒で（0.2 秒から。最後の歯は 2 回目のあと 0.8 秒で 60dB 消える）。
    最初は 3.6kHz を超える高さを 1 オクターブ下げていたが、連鎖 5・6 が連鎖 2・1 と同じ高さになり、「連鎖が進むほど高い」が崩れたので、折りたたまない
- **大きさをそろえた**: 耳の感度（A 特性）+ 小さなスピーカー風の 350Hz 以下のカット + 出口の 9.5kHz ローパスで重み付けした大きさを、ガラス・バーチャイム・鈴に合わせた。
  最初は RMS（重みなし）でそろえたら、置く音がガラスより 2.5〜5.5dB 大きく聞こえる（低い・中域の音は耳に大きく聞こえる）ことが分かったので、置く音は高さごとに RMS の目標を決めた
  （木琴 0.120 / 0.111 / 0.129 / 0.105、オルゴール 0.099 / 0.096 / 0.106 / 0.093。ガラスの先頭 0.25 秒の A 特性 −62.1dB に ±0.1dB）。シャラン（先頭 1 秒の RMS 0.07）・鈴（先頭 0.4 秒の RMS 0.1）は
  RMS をそろえるだけでガラスとの差が 1.2dB 以内（シャラン 6 種の最大 0.9dB・鈴 11 段の最大 1.15dB）。ピークは 0.52〜0.89（ガラスは 0.9 で正規化）。合成は 1 セットぶん 約 33〜40ms（ガラスは 60ms）
- **作っておく**: 波形のキーは `place:セット:番号` / `chime:セット:高さ` / `note:セット:段`（63 個）。起動後の空き時間に、いまのセットと次に替わるセットだけを 1 つずつ作る（42 個。
  セット 1 つぶん 21 個で、合わせて約 100ms）。セットが替わったら、使わないセットの波形は捨てて（メモリ 1 セット約 4MB で、2 セットまで）、次のセットを作り始める
- **確認**: 木琴の部分音 4 倍が 2.756 倍・3 倍より強いこと、オルゴールの 6.27 倍が 2.756 倍・5 倍より強いこと、シャランが低い音から順に駆け上がること、大きさのそろい、
  有限・最後が 0・固定シード・直流なし・22.05 / 44.1kHz、キーの付け方・セットの切り替えと波形の入れ替え・範囲外の番号・波形を作れない環境（`test/synth.test.mjs`・`test/feedback.test.mjs`）。
  実際のブラウザで、1000 点の手前（950 点）から連鎖を起こし、その手は `place:0` `chime:0` `note:0`、次の手は `place:1` が鳴り、セット 0 の波形が捨てられ、セット 1・2 が残ることを確認
- **耳では確認できていない**: 木琴・オルゴールの聴こえ方（木琴らしさ・オルゴールらしさ・「ポコッ」「ポロン」の気持ちよさ・シャランとの印象の違い）は、スペクトルと数値だけ。
  試聴用の WAV（置く音・ゲームの流れ。3 セット）を作って渡したので、聴いて調整してほしい

### ラインの光

- **満杯の枠**（`Renderer.lineGlow`）: ラインの外接の四角に、白い 2px のふち + 外側・内側にブロックの明るい色のにじみ。0.7 秒で、opacity 0 → 1 → 0.9 → 0 と
  scale 0.96 → 1.035 → 1。光の帯は流れる向き（縦は下、横は右）へ 0.43 秒で走り抜ける。星は 3 マスなら 5 つ、最大 12 つを、
  30ms おきに交互の辺へ
- **通り過ぎた跡**（`Renderer.trail`）: 列車の後ろが抜けた時刻（`wake` と同じ式）に、マスの縁が 0.3 秒光って引く。星は 1 マスに 1 つ。ライン + ラインの外で合わせて 9 マス（通路の入り口まで）
- **星**（`sparkSprite`）: 四方の星（先を細く、側面をへこませる）+ 小さな斜めの星 + 中心の白い点 + 根元だけのごく小さなにじみ。
  白（暖色寄り）と、ブロックの 7 色の明るい面で縁どったもの。色ごとに 1 回だけ描く
- 光る要素は最大 36 個の星 + ライン 1 つの枠 + 跡 9 マス。早送り・動きを減らす設定・遅い端末では抑える（README の「長い連鎖でもカクつかないように」）

### 背景の色

- 今の青（`#2451c4` / `#2e60d6`）を OKLCH に直すと L = 0.478, C = 0.187, h = 264°。**L をそろえたまま h だけを回す**と、白との対比は
  全色相で縁 6.15 以上・中央 4.98 以上（淡い側は 5.06 / 4.36 以上、濃い側は 8.87 / 7.42 以上）。sRGB に収まらない鮮やかさは、明るさと色相を保って縮める
- 色相ごとの見た目（実機の画面に重ねて確認）: 赤・桃・紫・青・緑は鮮やか。橙は茶、青緑・水色は落ち着いた色。80〜138° は同じ明るさだとオリーブに濁るので、
  落ち着く先にはしない（通り過ぎるだけ）
- **ゆっくり・毎回ちがう並び**（「回るのが少し早すぎる」「ずっと同じ順番ではなく、いろいろな並び順にしてほしい」への対応）。以前は、発動しない手が 5 回続くたびに
  色相が 27° ずつ（3 秒）、コンボが 1 つ増えるたびに 34°（1.4 秒）、5 の倍数のコンボ・Amazing 以上の連鎖・新記録は 0.16 秒で一気に、全消しは 1.9 秒で 1 周
  — どれも決まった向き・決まった幅だったので、同じ順に同じ色が並んだ。
  - **速さ**（いずれも約 1.6〜2.8 倍ゆっくり）: ふだんの色は 8 手ごとに 5 秒（5 手ごと・3 秒）、コンボは 2.2 秒（1.4 秒）、「一気に」は 0.45 秒（0.16 秒）、
    お祝いの色を見せる長さは 連鎖 2.2 秒（1.5 秒）・新記録 2.4 秒（1.7 秒）・全消し 3.8 秒（2.6 秒）、戻る長さは 3 秒（2 秒）、全消しの 1 周は 3.2 秒（1.9 秒）、ゲームオーバーで落ち着く先へ戻るのは 2.6 秒（1.8 秒）。
    1 回の重ねの上限（40° ごと）・最小の長さ（90ms）は同じ。変えやすいよう、`CALM_EVERY` / `CALM_MS` / `COMBO_MS` / `SNAP_MS` に定数でまとめた
  - **ふだんの色の並び**（`nextHue`）: 今の色から、向きと幅をばらして進む。幅は 45〜110°（一様乱数）、向きは 65% 前の向きのまま・35% 反対。最近の 4 色（今の色を含む）の
    40° 以内には落ち着かず（16 回まで引き直し、後半の 8 回は幅の上限を 170° に広げる。それでも決まらなければ、最近の色からいちばん離れた候補）、黄〜黄緑のオリーブ域は
    142° へ繰り上げる。濃さは重みつきで引く（標準 45%・淡い 30%・濃い 25%。淡い・濃いは続けて同じにしない。`nextTone`）。乱数は `Ambient` の引数 `rand`（既定は `Math.random`）なので、
    テストでは種を決めた乱数で毎回同じ並びを作れる
  - **コンボの進み方**（`comboStyle`）: コンボが始まるたびに 向き（±）・1 つ増えるごとの幅（22〜38°）・5 の倍数での幅（48〜88°）・濃さの回り始め（淡い・濃い・標準のどこから）を引き直し、
    そのコンボの間は変えない（コンボが途切れたら捨てる）。引数を省くと従来の固定値（34° / 60° / 淡い始まり）
  - 全消しの 1 周の向きも、ふだんの色が進む向きに合わせてばらす。Amazing 以上の連鎖の別の色への跳び（90〜130° / 5 以上は 150〜210°）・新記録（100〜140°）も向きと幅をばらす
  - テストで確認（`test/ambient.test.mjs`）: 種の違う 6 つの並びが、どれも違う並びになること、幅（40〜180°）・向き（両方）、最近の色に近づきすぎないこと（40° 以内は 360 回中 5% 以下、12° 以内は 0）、
    オリーブ域に落ち着かないこと、色相の輪の 8 区画以上を通ること、濃さが 3 種とも出て続けて同じにならないこと、コンボの進み方（向き・幅・濃さが 200 回の引き直しでばらつく）、1 周の向きが両方出ること
- **色が落ち着いている間は全面の層を使わない**: 背景の層（`#ambient`。全面の `position: fixed`）は、色が変わるたびに増える z-index を付けて opacity で重ねる作りで、
  覆い終わったあとも一番上の 1 枚が全面に残っていた。全面の合成される層が 1 枚あるだけで、操作中の毎フレームの仕事（レイヤーの更新・コミット）が増える
  （Chromium・CPU 4 倍遅く・ドラッグの場面の A/B 4 回の中央値で、層を外して `body` の背景にすると、1 フレームあたりのメインスレッドの時間が 10.6ms → 9.4ms）。
  そこで、落ち着いている間は背景を `body` の `background`（styles.css と同じ式のグラデーション）に直接描き、`#ambient` を `hidden` にする。色が変わり始めるとき（`lift`）だけ
  今の色の層（`this.settled`）を下に敷き、その上に新しい色を重ねて、覆い終わったら（`cover`。ほかに重ねている途中の層が無いとき）`body` に描き直して層を片づける（`settleOn`）。
  見た目は同じ（実際のブラウザで、画面の隅の色を 8 回に分けて読み、0.2 秒ごとに連続して変わり、落ち着く瞬間に色が飛ばないことを確認）
- `--amb-glow`（コンボ・ピンチ・色の変化の同系色）は、以前はルート `:root` に書いていたので、色が変わるたびに画面の全要素のスタイルを計算し直していた（長いタスクの原因の 1 つ）。
  使う 3 つの要素（`#fever` / `#danger` / `#sceneTint`）にだけ書く（使わない間は `hidden` / 不透明度 0 なので、書くコストはほぼ 0）
- **盤面の土台**（`.well-set`。マスの下の土台 `--plate`・くぼみ `--well`・くぼみの内側の影 2 つ・縁の線 2 つ・盤面のまわりの光と影）も、背景と一緒に変わる。
  最初は「盤面の青い土台は変えない」にしていたが、背景が赤・緑・橙になると青い盤面だけが浮いて見えるので、背景に合わせることにした
  （以前にあった「枠の線がコンボの色に光る」は #55・#56 で外した別のもの。今回は土台の面の色そのもの）。
  - 色の決め方（`boardLook`）: 今の青の土台の 8 つの色を OKLCH に直す（土台 L 0.418・C 0.183・h 265°、くぼみ L 0.359・C 0.141・h 268°、縁の線 L 0.66・0.79…。どれも h 263〜268°）。
    背景と同じ角度（色相 − 264.2°）だけ色相を回し、背景の濃さの段（soft は L +0.045・C ×0.85、deep は L −0.083・C ×0.9）と同じだけ明るさ・鮮やかさをずらす。
    sRGB に収まらない鮮やかさは明るさと色相を保って縮める。元の青のときは元の値そのもの。そのため、板は背景の縁の色より常に約 0.06（L）暗く、
    くぼみはさらに暗い（どの色相・濃さでもテストで確認）
  - 切り替え: 背景の層と同じ作り。盤面の土台の絵を 5 枚（背景の層 4 枚 + 最初から見えている今の青の 1 枚）重ね、背景の `show()` と同じ瞬間に、新しい色の層を一番上へ
    opacity 0 → 1（同じ長さ・同じ easing）、覆い終わったら下の層を外す。毎フレームの描き直しが起きるのは避けたいので、色の変数を動かす方式（`@property` の transition）にはしなかった
  - **直したバグ（土台がブロックを隠した）**: 土台の層には色が変わるたびに増える z-index を付けるが、以前は `#wellLayer` の `filter` が重ね合わせの文脈を閉じていた。
    土台の層ごとに `filter` を付け替えたとき、`#wellLayer` 自体の文脈が無くなって、増えた z-index が盤面の中（`#playfield`）へ漏れ、ブロック・プレビュー・ヒントの層より前に出た。
    その結果、最初の色変えのあと、盤面のブロックが土台に隠れて見えなくなった（見つけたのはユーザー。当時の確認は、空の盤面と層の opacity だけで、ブロックを置いた盤面の前後関係を見ていなかった）。
    `#wellLayer { isolation: isolate }` で文脈を閉じて直した。確認: 盤面にブロックを置き、`elementsFromPoint` で各ブロックの中心の並びを調べる
    （変更前は色変え後に 7 個中 7 個が土台に隠れ、修正後は 0 個）。ブロック 7 個・プレビュー 4 個・ヒント 4 個が、青 → 赤 → 緑へ変わる途中 → 紫（deep）→ 40 回の色変え
    のあとも、すべて土台より前。ヒントで 40 手（25 回の連鎖、色相の変化 21 回）遊んでも、100ms ごとの調べで、動いているブロックも含めて 15,339 回の観察のうち 0 回
  - 確認: 最初の青の盤面は、変更前と画素まで同じ（空の盤面を、画面の上から 780×1200px の範囲で比較、差 0）。切り替えの途中で、背景と土台の層の opacity が同じ値で進むことを確認
    （`getComputedStyle`。0.17 / 0.17 → 0.97 / 0.97）。赤（30°）・緑（150°）・紫（300°・deep）・青緑（200°・soft）・茶（60°）で、盤面が背景の色になじむことをスクリーンショットで確認

### 軽量化（ラグの原因を測って直した）

「全体的にラグい。めっちゃ軽くして、操作が快適になるように」への対応。**勘で削らず、先に測って原因を絞った。**

#### 測り方

- Playwright + Chromium（ヘッドレス）。画面 390×844・DPR 2。CPU を 4 倍遅く（`Emulation.setCPUThrottlingRate`。スマホ想定）。音は切る。
  メインスレッドの忙しさ = `Performance.getMetrics` の `TaskDuration` / 経過時間（**忙しさ**。1 に近いほど、メインスレッドが空かない）と、1 フレームあたりの ms（`TaskDuration` / フレーム数）、
  `requestAnimationFrame` の間隔（fps・33ms 超えのフレーム数）、長いタスク（PerformanceObserver の `longtask`）。内訳はトレース（`devtools.timeline`。スタイル再計算・レイアウト・Layerize・Commit…の自分の時間）
  と `cc`、スタイル無効化の追跡、CPU プロファイル（JS）で見た
- 場面（毎回同じ状態から）: **連鎖** = 保存した盤面から 1 手置いて、長い連鎖（数連鎖〜十数連鎖）を最後まで再生 / **ドラッグ** = トレイのピースを 60 回に分けて盤面まで運んで置く、を 5 回 /
  **ヒント** = 学習モードのおすすめで 14 手 / **何もしない** = 6 秒
- 描画は 2 通り: **ソフトウェア**（ヘッドレスの既定。canvas もソフトウェア）と、**GPU 風**（SwiftShader + `--enable-gpu-rasterization --enable-accelerated-2d-canvas`。canvas が GPU で描かれる。
  実機に近いのはこちらだが、SwiftShader 自体が CPU で動くので fps は実機より低く出る。メインスレッドの時間だけを見る）
- 比べる版: **before** = このブランチの元（main `eade150`）/ **after** = 今回 / **p59** = 演出を足す前（#59。軽かった頃）。同じ日・同じ環境で、版を交互に測った
  （環境でゆらぐので、日をまたいだ数字は比べない）

#### 原因（測って分かったこと）

1. **動いている要素 1 つにつき、ブロックを動かす間は毎フレーム仕事が来る**（いちばん大きい）。Web Animations / CSS アニメーションは、合成だけで動くので「主スレッドは空く」と思われがちだが、
   `requestAnimationFrame` が回っている間（= 連鎖を再生している間ずっと）は、動いている要素ごとに毎フレーム、スタイルの再計算とレイヤーの更新が主スレッドで走る。
   最小の例（40 個の div を 1 秒ずつ 3 回動かす。CPU 4 倍遅く。全体 3.6 秒のメインスレッドの時間）: 何も動かさず `rAF` だけ 266ms → opacity だけ 846ms → `transform` 891ms →
   scale + opacity 1001ms → translate・scale・rotate + opacity（星と同じ）**1408ms（5.3 倍）**。`rAF` を回さなければ、同じ 40 個が 120〜220ms と、ほぼ 0 のまま
   （スタイル再計算 18 回 / `rAF` ありは 218 回）。性質の数にも比例する（1 つ → 4 つで約 1.7 倍）。
   連鎖の最中に同時に動いている Web Animations は 平均 51 個（最大 91 個。p59 は最大 56 個）で、内訳は 星 17（最大 34）・光の跡 6（13）・1 文字ずつの文字 6（8）・かけら 5（14）・マスに満ちる色 2 ほか。
   星と光の跡は #60 で足したもの。つまり**ラインの光の演出がいちばん重かった**
2. **画面いっぱいの層が、使っていなくても置いてあるだけで重い**: 新記録の風船の canvas（`#sceneFront`）を空のまま置いておくだけで、連鎖の場面の忙しさが約 0.12 増える。
   ピンチの縁（`#danger`）・コンボの光（`#fever`）・背景の層（`#ambient`）も、opacity 0 や最前面で全面を覆ったままの層がある（背景を `body` の背景にするとドラッグが 1 フレーム 10.6 → 9.4ms）
3. **色が変わるたびに引っかかる**: `--amb-glow` をルート `:root` に書くと、画面の全要素（約 1,200 個）のスタイルを計算し直す。初めて表示する土台の層（36 マス）の描画も 1 回の長いタスクになる
4. **常に置いてある要素**: マスに満ちる色の 36 個は、何も満ちていなくても毎フレームのレイヤー更新に数える（隠すとドラッグが 1 フレーム 約 15% 軽い。ばらつきが大きいので、効果は 5〜15% 程度）
5. **ドラッグ中のピースを `left` / `top` で動かしていた**: 指が動くたびにスタイル再計算・レイアウト・描き直し（611 回の無効化）。`transform` にして `will-change: transform` で合成だけで動かす
6. **ヘッドレス特有で、実機には無いもの**: マウスの位置を見る当たり判定（`HitTest`）が毎フレーム 3〜5% 出る（タッチの端末には無いはず）。canvas をソフトウェアで描くと、画面の密度の 2 乗に比例して重い
   （ここを見誤って、最初の canvas の試作は「ソフトウェア描画では速くならない」と出た。GPU で描く設定にして初めて 7 分の 1 になると分かった）

#### 直したこと

- **小さな演出（星・宝石のかけら・ラインの光の跡）を、要素ではなく canvas に描く**（`fx2d.js` の `FxCanvas`。星 `sparkles.js`・かけら `shards.js`・光の跡 `rims.js`）。
  canvas は 2 枚だけ（星とかけらは `.fx2` = ブロックの前、光の跡は `#fxLayer` = 以前の光る要素と同じ重なりで、動いているブロックの後ろ）。粒は `{ start, end, draw(ctx, now) }` で、時刻で位置を決める
  （間引いても速さは変わらない）。動きは以前の Web Animations と同じ式（`bezier` = CSS の `cubic-bezier`、`easeOut`、`sparkPose` / `shardPose` / `rimPose`。テストで形を確認）。
  絵は色ごとに 1 回だけ描いた小さなもの（星 64px・宝石 64px・光の枠）を、拡大・回転・濃さを変えて貼る。光の枠は、以前の CSS の `box-shadow`（外側のにじみ・外側の細い白・内側のにじみ・内側の白いふち）を
  そのまま描き直した。同時に 星 36 個・かけら 14 個（全消しは 42）まで。何も描いていない間は canvas を `hidden` にして、層ごと外す。一時停止は canvas の時計も止める。
  canvas が覆う範囲は、必要なぶんだけ（星・かけら = 盤面 + 1.6 マスの余白、光の跡 = 盤面 + 通路 + にじみの余白）
- **GPU が無い端末では、描く細かさと頻度を落とす**（`Renderer.tuneFxDensity`・`softwareRendering`）: ソフトウェア描画の canvas は、中身を書き換えるたびに画面の面積ぶんの写しが要るので、
  最初の移植は GPU なしだと逆に重くなった（連鎖の忙しさ 0.65 → 0.92）。起動後の空き時間に WebGL の描画装置の名前（SwiftShader・llvmpipe・Basic Render など）で見分け、そのときだけ
  細かさを 1 倍（以前は DPR 2）に下げ、2 コマに 1 回の更新（30fps）にする（`FxCanvas.setEvery`。間引くコマは canvas に触らない）。GPU のある端末は変えない（細かさ 2 倍・毎コマ）。
  描画装置が分からなければ GPU ありとして扱う
- **画面いっぱいの層は、使っていない間は画面から外す**: `#sceneFront`（風船の canvas。描き始めに出して、終われば `hidden`）・`#danger` / `#fever`（`setVeil`。出るときは opacity 0 で描かせてからふわっと出し、
  消えるときは薄くなってから外す）・`#ambient`（色が落ち着いている間は背景を `body` に直接描く。「背景の色」の節）
- **`--amb-glow` はルートではなく、使う 3 つの要素（`#fever` / `#danger` / `#sceneTint`）にだけ書く**。長い連鎖の途中の色の変化で、画面全体のスタイル再計算が走らない
- **マスに満ちる色の 36 個は、満ちている間だけ画面に出す**（`tintCell`。終わった・取り消されたら `hidden`。あとから別の色で満ち直しているときは外さない）
- **ドラッグ中のピースは `transform` だけで動かす**（`translate(指の位置) + 盤面と同じ回転`。`will-change: transform`）。`left` / `top` は書かない。移動量は以前と同じ（差 0.006px 以下）
- **最初に使う瞬間に作ると止まるものは、起動後の空き時間に 1 つずつ作っておく**: 星・かけら・光の枠の絵（`warmJobs`）と、音のセットの波形（`Sfx.warmSoon`）。
  音は いまのセットと次のセットの 42 個で合わせて約 100ms なので、1 つずつ間をあけて作る
- 変えていないもの: ルール・得点・演出の見た目の絵と動き（canvas の絵は以前の DOM の絵と同じ式）・音の鳴り方（セットを除く）
